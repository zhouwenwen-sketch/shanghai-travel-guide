# 原四家首页酒店及关联内容恢复方案

日期：2026-10-04。状态：已完成代码和本地 API 取证，尚未修改业务代码或数据库。

## 目标与边界

首页推荐恢复上海和平饭店、上海凯宾斯基大酒店、上海外滩南京东路亚朵酒店、上海艾迪逊酒店，并恢复原封面、星级图、标签、地址、电话、价格、简介、评分、展示点评数、房型及演示点评。

基线来自仓库内原有演示数据；本次不是联网核实真实酒店价格或星级。只调整 NestJS 酒店初始化/修补相关文件，不启用 Java，不涉及 AI、POI 内容、预订规则或前端页面重构。

| 2 | 上海锦江饭店 | 历史建筑、市中心 | 0 | 0 | null | 4.7 / 860 |

这与 `server/src/scripts/seed.ts:8-15` 的简化种子数据完全一致。

### 根因

1. `server/src/scripts/seed.ts:13-14` 只创建两家酒店，其中锦江饭店并非原四家之一。
2. 原设施标签没有迁入，被改成每家两个标签；和平饭店只保留一个改写的房型，脚本没有创建任何 reviews。
3. 种子遗漏 `starimg_url`；和平饭店的评分、点评数量、地址、简介等也被改写。
4. `seed.ts:8` 只要检测到任何酒店就退出。已有两家酒店的数据库即使重复执行 seed，也不会补齐内容。
5. 首页 `src/views/recommend-list.vue:30,45` 全量循环返回酒店和标签；服务 `server/src/hotels/hotels.service.ts:15,37-39,70` 完整读取推荐酒店、标签、房型、点评，没有只取两家或两个标签的逻辑。

### 权威恢复来源

- 同文件 `103-110`：四家酒店共 8 条点评及回复。
- 同文件 `142-145`：四家酒店共 27 个标签。

### 允许使用的现有机制

- `DatabaseService` 现有 Prisma 客户端：`$transaction`、`hotels.findMany/create/update`、关系表 `upsert/deleteMany/createMany`。
- `server/prisma/schema.prisma:63,76,84` 和生成客户端类型确认了以下复合唯一键：

- hotels.name **没有唯一约束**，不能直接使用 `upsert({where:{name}})`；先查精确名称和身份字段，检查歧义，再按真实 ID 操作。
- `server/package.json` 中已有 `npm run seed`，优先复用，不增加公开 HTTP 接口。

## Phase 2：幂等恢复现有库，保留关联

在 `server/src/scripts/seed.ts` 的酒店部分使用可测试的恢复函数：

1. 写入前读取目标酒店和推荐列表，输出将修改/新增的酒店清单，并保存涉及酒店及其子表的恢复前快照。检查重复同名酒店、身份冲突和额外推荐；歧义时不写入。
2. 按精确名称并核对电话等已有身份字段查找四家原酒店。已有和平饭店保留当前 ID，更新为原内容；其他三家缺失则新建，使用数据库生成 ID。
3. 以 `实际 ID → 酒店身份` 映射写入标签、房型和点评。四家目标酒店的演示标签恢复为原集合；只在这些酒店范围内替换已识别的简化种子标签。遇到无法归类的额外用户数据，报告冲突，避免静默覆盖。
4. 房型按 `(hotel_id,name)`、点评按 `(hotel_id,review_user,date)` 幂等补齐或更新已确认的演示记录。和平饭店“豪华大床房”已有记录应保留 ID，恢复 42m²、大床1.8m 等原字段；不要叠加出第二条同名房型。
5. 将四家酒店设为推荐。对本次已确认的简化演示“上海锦江饭店”仅取消推荐，保留酒店记录、房型和业务关联。不把 ID 2 改名成凯宾斯基，不删除锦江饭店。
6. 酒店、标签、房型、点评和推荐标记在同一个事务内更新；任何阶段失败均回滚。
7. 将“已有任意酒店就退出”的条件改为酒店级恢复逻辑。原有 POI 初始化分支保持既定行为，酒店修补重复执行不能重复插入 POI。
8. 初始化函数使用 try/finally 关闭应用连接；失败返回非零退出码。执行前确认目标为配置中的本地开发库。

重要约束：

- 旧 ID 2 是凯宾斯基，当前 ID 2 是锦江饭店，严禁按旧 ID 覆盖当前酒店。
- 保留所有订单、收藏、浏览历史、行程项目的 hotel_id；已保存订单的 nightly_price/total_price 不随酒店恢复改变。
- 不执行清库、重置自增、直接导入整份 V2 SQL、全表取消推荐或全表删除标签。
- 如果当前库新增了其他推荐酒店，需要在写入前列出差异；不能为了“恰好四家”静默修改无关酒店。
- 普通顺序重复执行必须幂等；运行数据修补时使用单个进程，避免无酒店名称唯一约束下并行创建。

验收：在目前两酒店的库上执行后，首页推荐为原四家；酒店总表可以保留非推荐的锦江饭店。第二次执行后酒店及子表数量、ID 和内容不变。业务关联仍指向原酒店身份。

## Phase 3：接口与页面验收

主要新增/修改文件预计为：

1. 新增 `server/src/scripts/original-hotels.ts`：原始内容 fixture。
