# 酒店搜索性能实测

测试日期：2026-09-23。环境为 Windows、Node.js v24.14.0、MySQL 8.0.45、Intel i5-1240P、16 GB 内存。数据由固定种子 `20260922` 生成；每个场景预热 5 次、采样 20 次。原始输出保存在 `benchmark-results/`。

## 5 万条数据：旧全量接口与新分页接口

两组测试使用相同数据、相同服务进程和相同索引。分页接口每次返回 24 条。

| 场景 | 旧接口 p95 | 分页接口 p95 | p95 降幅 | 旧响应 | 分页响应 | 传输量降幅 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 全部酒店 | 1706.6 ms | 20.8 ms | 98.8% | 17393.2 KB | 8.5 KB | 99.95% |
| 区域 + 星级 | 82.9 ms | 11.8 ms | 85.7% | 542.9 KB | 8.5 KB | 98.43% |
| 价格区间 | 674.7 ms | 12.3 ms | 98.2% | 4553.6 KB | 8.4 KB | 99.81% |
| 模糊关键词 | 2113.7 ms | 28.7 ms | 98.6% | 17393.2 KB | 8.5 KB | 99.95% |

这些数字衡量本机 API 请求，不等同于浏览器 FCP/LCP。旧接口会序列化并传输全部匹配酒店；分页接口仍会执行总数统计，但只查询和序列化当前页字段。

## 索引执行计划

在 1 万条数据上先保存无索引计划，再试建索引并复测：

- `(area, star_level, id)`：区域 + 星级查询从主键扫描 747 行取得 24 行，变为覆盖索引查找；该执行节点实测约从 0.423 ms 降至 0.124 ms。
- `(price, id)`：价格查询从扫描 10,000 行并排序，变为覆盖索引范围扫描并直接按索引顺序取 24 行；该执行节点实测约从 6.62 ms 降至 0.074 ms。
- `name LIKE '%关键词%'` 仍不能利用普通 B-tree 前缀，当前分页后在 5 万条全匹配数据上的 API p95 为 28.7 ms，暂不引入全文检索。
- 第 2,081 页的 `OFFSET 49,920` 会扫描 49,944 个索引项，实测 15.6 ms。当前页码上限为 10,000；若未来深页性能成为问题，再增加游标分页。

因此正式 Prisma schema 仅加入上述两个有执行计划证据的索引。堆内存数据是请求结束后的抽样值，受垃圾回收时机影响，不作为简历中的精确降幅指标。

## 可用于简历的表述

针对 5 万条酒店数据，将全量查询和前端筛选改为服务端组合筛选、稳定排序与分页，并基于 `EXPLAIN ANALYZE` 增加复合索引；同机 20 次采样中，全量搜索接口 p95 从 1706.6 ms 降至 20.8 ms（下降 98.8%），响应体从 17.0 MB 降至 8.5 KB（下降 99.95%）。
